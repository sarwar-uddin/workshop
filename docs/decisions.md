# Decisions

A short record of choices that would be non-obvious to a new reader (or to future me). Newest last. Each entry says what was decided, why, and what it costs.

## 2026-11-27: Stock is a column plus a ledger, updated in one transaction

**Decision:** `products.stock_quantity` holds current stock. From M8/M9, every change also inserts a `stock_movements` row, in the same transaction.
**Why:** reading stock stays a cheap column read, the ledger explains every change, and the `>= 0` check can guard the column directly.
**Cost:** the two can drift if any code changes stock outside the transaction. So stock is **not** writable through the product API; only inventory operations change it.
**Rejected:** computing stock as `SUM(quantity_delta)` every time. Always correct, but slower and harder to constrain.

## 2026-11-27: Case-insensitive SKUs and category names

**Decision:** unique indexes on `lower(sku)` and `lower(name)`. The original casing is stored as entered.
**Why:** humans treat `abc-1` and `ABC-1` as the same code. The index enforces this even under concurrent requests.

## 2026-11-27: Money is `numeric(12,2)`, a string in JS and in JSON

**Decision:** exact decimal in the DB. The `pg` driver returns it as a string, and the API sends and accepts strings like `"1850.00"`.
**Why:** floats can't represent most decimal amounts exactly (`0.1 + 0.2 !== 0.3`). Totals (M8) will be calculated in SQL or with exact decimal arithmetic, never with JS floats.

## 2026-11-27: Archive, don't delete

**Decision:** products have `status: active | archived`, and there is no DELETE endpoint. Categories use `ON DELETE RESTRICT`.
**Why:** orders will reference products, and deleting a product would destroy order history.

## 2026-11-27: `uuidv7()` primary keys

**Decision:** UUIDs generated by PostgreSQL 18's built-in `uuidv7()`.
**Why:** IDs can't be guessed and are safe to expose. They're also time-ordered, so new rows go at the end of the index instead of random places (unlike v4).

## 2026-11-27: Let constraints decide, then translate the error

**Decision:** the service attempts the insert or update and maps Postgres errors: `23505` (unique) → 409 `SKU_TAKEN`, `23503` (FK) → 400 `CATEGORY_NOT_FOUND`.
**Why:** "check first, then insert" has a race window: two requests can both pass the check. The unique index is the real guarantee, so the code interprets its error.
**Note:** Drizzle wraps driver errors, so `getPgError()` also looks at `error.cause`.

## 2026-11-27: Strict input schemas

**Decision:** Zod `strictObject` for request bodies. Unknown keys are rejected with a 400.
**Why:** a client sending `stockQuantity` gets told it can't do that, instead of having the field silently ignored.

## 2026-11-27: No service layer until there are rules

**Decision:** listing products went straight from route to repository. The service appeared only when create/update brought real rules.
**Why:** a pass-through layer is ceremony. Categories still have no service or repository; split them out when they gain writes.

## 2026-11-27: A `pg` pool error listener is required

**Decision:** `pool.on("error", …)` logs the error.
**Why:** found while testing. When Postgres drops an *idle* pooled connection, the pool emits `'error'`, and with no listener Node crashes the whole API. Now a DB outage returns 500s and the API recovers when the DB comes back.

## 2026-11-28: API tests hit a real PostgreSQL test database

**Decision:** Vitest + Supertest against `workshop_test` on the same Postgres server, migrated with the real migrations, with every table truncated before each test. No mocked database.
**Why:** most of the API's guarantees live in Postgres: the case-insensitive unique SKU, the FK, CHECK constraints, numeric money coming back as `"1850.00"`. A mocked DB would test the mocks. Running the real migrations also catches a broken migration.
**Trade-off:** test files run one at a time (shared database), and Docker must be up. That's fine at this size. Revisit with one database per worker if the suite gets slow.
**Safety:** the test setup refuses any database whose name doesn't end in `_test`, because it wipes every table.

## 2026-11-28: `app.ts` builds the app, `index.ts` listens

**Decision:** split the Express app from `app.listen()`.
**Why:** Supertest needs the app without a bound port. It's also where a future graceful-shutdown handler goes, without touching routes.
